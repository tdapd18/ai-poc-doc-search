# 실제 Windows 공유폴더 검색 모드 — 운영·보안 가이드

> **현재 상태**: 합성 Windows 공유(가상 데이터)로만 검증했다. 실제 회사 PC·공유폴더에는 연결하지 않았고, 회사 자료는
> Claude Code·외부 AI 서비스로 전송한 적이 없다. 실제 연결은 **보안 승인 후 별도로 §6 체크리스트에 따라** 수행한다.

## 1. 실행

```powershell
cd ai-poc-doc-search
python -m pip install -r requirements.txt
.\scripts\run_real.ps1                 # = $env:APP_MODE="real"; python -m streamlit run app.py
```
- `APP_MODE` 가 없으면 기존 **데모(가상 데이터) 모드**로 동작한다(기본값, 기존 기능·테스트 유지).
- 홈 폴더(설정·색인·공유 등록·감사 로그): `%LOCALAPPDATA%\ActuarialDocSearch` (`APP_HOME` 로 변경).

## 2. 첫 실행 흐름 (초기 설정 화면)

| 단계 | 내용 |
|---|---|
| ① 보안 모드 | **메타데이터 전용(기본)** 또는 본문 검색. 본문 검색은 보안 승인 확인 체크 + 승인 참조(담당자/문서 번호) 입력이 있어야 켜진다. 모드를 바꾸면 기존 색인을 **모두 삭제**(VACUUM) |
| ② 공유폴더 등록 | UNC 경로(`\\서버\공유\폴더`) 등록. 관리자 공유(`C$`)·장치 경로(`\\?\`)·드라이브 경로·겹치는 경로 거부. 공유별 제외 패턴 |
| ③ 연결 테스트 | 경로 접근·응답 시간·읽기 권한 표본·형식별 파일 수 점검. **파일 내용을 읽지 않음**. 실패 원인별(권한/경로/네트워크) 조치 안내 |
| ④ 색인 생성 | 모든 공유의 연결 테스트가 성공해야 활성화. 진행 상황 표시, 결과는 건수 중심으로 요약(파일명 미노출) |

## 3. 권한 모델 (Windows 로그인 계정)

- 앱은 사용자 PC에서 **그 사용자 계정으로** 실행된다. 파일 접근권한은 **운영 체제가 판정**하며, 앱은 ACL 을 해석·복제하지 않는다.
  권한의 근거는 "그 파일을 지금 실제로 열 수 있는가"(`check_open`)다. (`os.access` 는 Windows 에서 ACL 을 반영하지 않아 사용하지 않음)
- 색인 시점: 읽을 수 있는 파일만 색인(접근 거부는 건수만 집계). 증분 갱신에서도 **변경 없는 파일의 권한을 매번 다시 확인**
  (ACL 변경은 수정 시각을 바꾸지 않기 때문).
- 조회 시점: 결과 행·원문 미리보기·AI 근거·이전 답변·캐시 적중마다 **표시 직전에 파일 열기로 재검증**. 삭제·권한 회수·공유 불가·잠금·확인 불가는 모두 숨김(fail-closed).
- 색인은 계정별 로컬 파일이다. 다른 Windows 계정으로 열리면 색인을 폐기한다.
- 한계: 대량 필터·건수·필터별 개수는 색인 시점 스냅샷을 쓰므로, 권한이 회수된 직후 **일치 건수 같은 부가정보에는 그 문서가 잠시 반영**될 수 있다(본인이 이전에 접근 가능했던 문서에 한함). 내용·제목·경로는 표시되지 않는다.

## 4. 안전한 변경 처리

| 상황 | 조회 | 색인 갱신 시 |
|---|---|---|
| 파일 수정 | "원본 변경됨·색인 갱신 필요" 표시 | 지문(크기:수정시각) 변경 감지 → 다시 추출 (내용 해시가 같으면 지문만 갱신) |
| 파일 삭제 / 이름 변경 | 즉시 숨김 | 색인·조각 삭제(`secure_delete`로 DB 파일에서도 덮어씀). 이름 변경 = 삭제 + 신규 |
| 읽기 권한 회수 | 즉시 숨김(검색·캐시·미리보기·AI 근거·이전 답변) | 색인에서 제거, '읽기 권한 없음 N건'으로 집계. 복구되면 다음 갱신에서 다시 색인 |
| 파일 잠금 / 일시 네트워크 오류 | 숨김 | 기존 색인 **유지**(삭제 안 함), 재시도 대상으로 보고 |
| 공유 전체 접근 불가(VPN 단절) | 그 공유 결과 숨김 | 그 공유의 색인 **유지**, "연결할 수 없음" 보고. 복구되면 재색인 없이 다시 검색 |
| 하위 폴더 목록 거부 | — | 그 폴더 아래 문서 제거(fail-closed) |
| 하위 폴더 일시 오류 / 파일 수 한도 | — | 확인하지 못한 문서의 삭제 판단 보류 |
| 읽는 중 파일 변경 | — | 불완전한 내용은 색인하지 않고 기존 색인 유지, 재시도 |
| 공유 해제·사용 안 함 | — | 그 공유 문서 전부 삭제 |

일시 오류로 숨겨진 결과(오프라인 등)는 **캐시하지 않는다**(복구 후 곧바로 정상 결과가 나오도록).

## 5. 색인 수준과 보안 통제

| | 메타데이터 전용 (기본) | 본문 검색 |
|---|---|---|
| 저장 | 이름·경로·형식·수정일·크기 | + 추출한 본문 조각 (이 PC 로컬 DB) |
| 파일 내용 열람 | **없음** (권한 확인용으로 열었다 바로 닫음) | 있음 |
| 전환 조건 | 기본값 | 승인 확인 + 승인 참조 기록(감사 로그에 모드 변경 기록) |
| 모드 변경 | 기존 색인 전체 삭제 | 기존 색인 전체 삭제 |

- 승인 확인은 **절차적 통제**다(사용자가 설정 파일을 직접 수정할 수 있음). 승인 기록 없이 `index_mode=full_text` 만 써넣으면 로드 시 메타데이터 전용으로 되돌린다.
- 외부 전송 없음: 앱은 파일 내용·검색어를 어디로도 보내지 않는다. LLM 은 기본 비활성(`LLM_PROVIDER=none`)이며 실제 LLM 연결은 구현되어 있지 않다.
- 감사 로그(`audit.log`): 모드 변경·공유 등록/해제·연결 테스트·색인 실행의 **건수/상태만**. 파일명·경로·본문·검색어 없음.
- 로컬 색인 파일은 사용자 프로필 폴더에 저장된다(posix 에서는 600 권한). **DB 파일 암호화는 미구현**(후속: DPAPI/SQLCipher). 분실·반출 위험이 있는 PC 라면 본문 검색을 켜지 말 것.
- 설정 화면의 '색인 삭제' 로 언제든 로컬 색인을 지울 수 있다.

## 보안 보완 (표시 직전 재검증 · 로컬 색인 보호)

- **목록·건수·필터 재검증**: `SearchEngine.list_visible_documents()` 는 문서명·경로를 돌려주기 전에 `verify()`(실제 열기 시도)를 적용한다.
  첫 화면의 문서 목록, 접근 가능 문서 수, 유형별/위치별 건수, 필터 선택지는 모두 이 결과(또는 `refine()` 로 좁힌 결과)에서만 만든다.
  색인 이후 권한이 회수·삭제·오프라인이 된 파일은 **색인 갱신 없이도** 즉시 사라지고, 복구되면 다시 나타난다.
- **원본 수정 후 과거 문단**: 색인 이후 바뀐 파일은 '원본 변경됨'으로 표시하되 검색 결과 문단·미리보기·일치 위치·AI 근거·이전 답변에서 과거 본문을 보여주지 않는다. 색인 갱신 후 새 내용으로 표시된다.
- **로컬 색인 저장**: (아래 "최종 보안 보완"에서 *검증 후 차단* 방식으로 변경 — 앱이 Windows 폴더 권한을 바꾸지 않는다) `secure_delete`, 임시·저널을 디스크에 만들지 않음(`temp_store`/`journal_mode=MEMORY`),
  비정상 종료로 손상된 DB는 덮어써 폐기 후 재생성, 기동 시 백업·복사본·임시·저널 잔존 파일을 덮어써 삭제, OneDrive 등 동기화 폴더 경고(설정 화면 "로컬 색인 저장 보안").
- **한계(미구현/미검증)**: DB 자체 암호화는 하지 않는다(BitLocker 등 디스크 암호화 필요). SSD·저널링 파일시스템에서는 덮어쓰기 삭제가 완전한 소거를 보장하지 않는다.
  실제 NTFS ACL 반응은 실기 검증(W-체크리스트)에서 확인해야 한다. 목록 조회는 파일마다 열기를 시도하므로 문서가 매우 많은 공유에서는 화면 갱신이 느려질 수 있다.

## 최종 보안 보완 (실무 전환 전)

> 구현 완료 ≠ 합성 테스트 통과 ≠ Windows 실기 검증 완료. 아래는 **구현·합성 테스트까지**이며 실기 검증은 W-14~W-24 로 남아 있다.

### 검색 총건수 (P0)
- 실제 모드 접근 제어기는 `exact_counts=False` 다. 전체 일치 문서를 매번 열어 권한을 확인하면 네트워크 공유에서 느려지므로,
  **권한 확인이 끝난 표시 결과만** 안내한다: `접근 확인된 검색 결과 N건 표시`. '총 N건'·'상위 N건' 같은 전체 수 암시 표현을 쓰지 않는다.
- `total_matched` 는 검증된 표시 결과 수, `metadata_only_count` 도 표시 결과 안에서만 계산한다(권한 없는 문서 존재를 건수로 추론 불가). 데모 모드는 기존대로 정확한 총건수를 표시한다.
- 필터 선택지·접근 가능 문서 수·유형별/위치별 건수는 앞 절의 `list_visible_documents()` 재검증 결과에서만 만든다.

### 화면에 남은 검색 결과 (P0)
- 렌더링할 때마다 `SearchEngine.revalidate_response()` 로 세션의 이전 응답을 재검증한다(열람 가능·내용 해시·변경 여부). 하나라도 실패하거나
  일시 장애로 일부가 거부됐던 응답(volatile)이면 **자동으로 재검색**하고 안내를 표시한다. 회수된 파일명·UNC 경로·문단·미리보기·근거·이전 답변이 남지 않으며, 권한/네트워크가 복구되면 다음 렌더링에서 다시 표시된다.

### 로컬 색인 저장 위치 (P0) — 검증 후 차단
- 앱은 Windows 폴더 권한을 **변경하지 않는다**(`icacls /inheritance:r` 등으로 SYSTEM·관리자·관리형 보안 권한을 제거하면 회사 중앙 정책과 충돌할 수 있음). 대신 `icacls <경로> /save` 로 DACL 을 SDDL(SID 기반·언어 독립)로 **읽기만** 하고,
  Everyone/Users/Authenticated Users/Domain Users 등 넓은 범위에 허용 ACE 가 있는지 폴더와 `index.db` 모두 확인한다. 명령이 성공했다는 사실만으로 안전하다고 판단하지 않는다.
- 판정: 넓은 접근 있음 / 권한 판독 실패·예외 → **색인 생성 차단 + 본문 검색·표시 차단**(파일명 검색만). OneDrive 등 동기화 폴더 → **본문 색인·본문 표시 차단**(메타데이터 색인은 허용). 설정 화면에 원인을 안내하며 경로·계정 같은 내부 정보는 싣지 않는다.
- 차단 중에도 원본 공유폴더는 읽기 전용으로만 접근하며 어떤 파일도 수정·삭제하지 않는다. 안전한 경로를 확보해 앱을 다시 시작하면 해제된다. (`APP_HOME` 으로 회사가 승인한 로컬 경로 지정)
- 한계: 개별 사용자(다른 직원 계정)에게 직접 부여된 ACE 는 넓은 범위인지 판단할 수 없어 검사하지 않는다. 현재 계정의 SID 와 비교하는 정밀 검사는 후속 과제.

### 색인 삭제·초기화·복구
- 색인 수준 변경·색인 삭제는 `perform_index_reset()` 을 거친다: 먼저 `reset.pending` 표식을 쓰고 삭제(VACUUM 포함) 후 `count==0` 을 확인한다. 실패하면 `IndexResetError` 를 사용자에게 알리고,
  이전 본문이 남아 있을 수 있으므로 본문 표시를 차단하며, 앱을 다시 시작해도 표식이 있으면 삭제를 마무리한다. 성공하면 검색 캐시를 비운다.
- 손상된 `index.db`: 시작 시 `quick_check` 로 감지 → 덮어써 폐기 후 새로 생성(알림 표시, 감사 로그 `index_recovered`). 삭제조차 불가하면 임시 메모리 색인으로 시작하고 색인·본문을 차단한다. 복구 후에는 일반 색인 절차(권한 재확인 포함)로 다시 만들므로 접근 불가 문서가 되살아나지 않는다. **색인은 파생 데이터이며 원본 공유폴더 파일은 어떤 경우에도 변경되지 않는다.**
- **SQLite 저널 설정 위험**: `journal_mode=MEMORY`·`temp_store=MEMORY` 는 변경 전 본문 페이지가 디스크 저널/임시파일로 남는 것을 막지만, 쓰기 도중 프로세스·전원이 갑자기 종료되면 DB 가 손상될 수 있다. 복구 방안: 다음 실행에서 `quick_check` 실패 → 폐기·재생성 → '색인 생성' 재실행(원본에서 재생성). 손상 빈도가 높거나 재색인 비용이 큰 환경이면 `journal_mode=DELETE` 로 바꾸는 것을 검토하되, 이 경우 삭제된 저널 파일 조각이 디스크에 남을 수 있다는 점을 보안 담당자와 협의한다.
- **미구현·제약**: SQLite DB 자체 암호화는 **구현하지 않았다**(BitLocker 등 디스크 암호화에 의존). 덮어쓰기 삭제는 SSD·저널링 파일시스템·백업/스냅샷/복원 지점에서 **완전한 삭제를 보장하지 않는다**.
